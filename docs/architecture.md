# Архитектура: Food Supplier Finder

Сервис поиска и сравнения поставщиков продуктов питания.
Прототип: веб-приложение с прозрачным «живым» поиском по нескольким источникам,
LLМ-структурированием собранных данных и инструментами для принятия решения.

## 1. Ключевая идея

Классический каталог поставщиков (статичная база) быстро устаревает и не показывает,
*откуда* взялись данные. Мы делаем наоборот: **поиск собирается на глазах у пользователя**
— как поисковик, но с выходом не на ссылки, а на готовые карточки поставщиков:

1. Пользователь вводит **товар** (например «мука пшеничная в/с») и **регион**.
2. Сервис в реальном времени опрашивает несколько независимых источников.
3. Дедуплицирует домены, обогащает каждую карточку (цены, МОК, сертификаты,
   доставка, контакты), где может — автоматически.
4. Показывает **прозрачный пайплайн**: пользователь видит каждый этап и
   источник каждого факта в карточке (`fact ↔ source URL`).
5. Дает инструменты решения: сравнение, заметки, RFQ-рассылка, экспорт.

## 2. Стек и обоснование

| Слой | Выбор | Почему |
|---|---|---|
| Backend | Python 3.12 + FastAPI | async из коробки — нужно параллельно опрашивать 3+ источника; SSE-стриминг прогресса одной строкой кода; быстрая разработка прототипа |
| Хранилище | SQLite | нулевой ops-бос, один файл, для прототипа и демо достаточно; схема мигрируется тривиально на Postgres |
| Frontend | Ванильный JS + SSE, без сборщика | прототип должен запускаться `pip install && ./run.sh` без node_modules; React здесь — оверкилл, оценивается UX, а не фреймворк |
| Прогресс | Server-Sent Events | однонаправленный стрим этапов идеально ложится на «прозрачность процесса» |
| LLM | gpt.ai-tools.su (OpenAI-compatible): gemma4:31b — дешёвые задачи, gemini-3.8-flash-high — структурирование | двухуровневая маршрутизация: 90% вызовов дешёвые; сложные — только на финальном извлечении |

## 3. Источники данных (plural, с graceful degradation)

| Источник | Что дает | Отказоустойчивость |
|---|---|---|
| **XMLstock: Яндекс XML** | региональная выдача (`lr=`) — основные кандидаты-домены, сниппеты | при ошибке — просто меньше результатов, поиск не падает |
| **XMLstock: Google XML** | второе мнение + оптовые агрегаторы | аналогично |
| **optlist.ru** (Playwright) | отраслевая база оптовиков: готовые контакты, регионы, описание | сайт за Anubis PoW → если Playwright не справился/нет — этап помечается «пропущен», остальное работает |
| **Госплан API (44-ФЗ контракты)** | поставщики, реально поставлявшие товар госзаказчикам + **фактические цены контрактов** | публичный API; при недоступности этап пропускается |

Любой источник может упасть — пайплайн продолжается, в UI видно, что источник
недоступен, и почему. Это осознанное решение: для демо лучше «частичный результат
с честным статусом», чем «сервис недоступен».

## 4. Пайплайн поиска (этапы = события SSE)

```
[1] plan        — LLM-планировщик строит поисковые запросы из ТЗ пользователя
                  (простая модель; «мука пшеничная» → «мука оптом», «мука производитель»...)
[2] serp        — Яндекс XML + Google XML по региону, параллельно
[3] optlist     — optlist.ru по категориям (Playwright, может быть пропущен)
[4] gosplan     — 44-ФЗ: поставщики + цены исполненных контрактов по товару
[5] merge       — дедупликация по домену/ИНН, слияние фактов, рейтинг источника
                  (госконтракт > отраслевой каталог > органический поиск)
[6] enrich      — обход сайтов-кандидатов (лимит!): телефон/email/адрес,
                  цены regex-проходом, LLM-fallback на сложных страницах
[7] structure   — LLM собирает финальную карточку поставщика и «причины связаться»
[8] done        — результат записан в БД, доступен экспорт
```

Каждый этап шлёт события `{stage, status, found, message}`. UI рисует чек-лист
этапов с live-счётчиками («SERP: +18 доменов…»), карточки появляются по мере готовности.

## 5. Модель данных (SQLite)

```
searches   (id, query, region, status, created_at, stats_json)
suppliers  (id, search_id, name, domain, inn, city, region, phones, emails,
            site, description, categories, price_min, price_max, price_note,
            min_order, delivery, certificates, gov_contracts_count,
            gov_contracts_value, relevance, reasons, sources_json,
            enrichment_status, created_at)
notes      (id, supplier_id, text, created_at)          -- заметки пользователя
rfq_log    (id, search_id, supplier_ids_json, subject, body, sent_at, status)
```

`sources_json` — provenance: каждый атрибут карточки со ссылкой на источник
(«цена 42 ₽/кг ← госконтракт №12345», «телефон ← optlist.ru»).

## 6. Функции принятия решения

- **Релевантность и причины** — LLM формирует человеческое объяснение, почему
  поставщик подходит под запрос («поставлял муку в школу №12, 3 контракта»).
- **Сравнение** — таблица всех найденных поставщиков по ключевым полям,
  сортировка по цене/количеству госконтрактов/релевантности.
- **Заметки** — приватные комментарии к поставщику.
- **RFQ-рассылка** — генерация письма-запроса КП (LLM: грамотный РФК с ТТХ),
  отправка через SMTP на все email найденных поставщиков, лог отправки.
- **Экспорт** — XLSX (полная таблица) и CSV (для Google Sheets).

## 7. Безопасность

- Все ключи в `.env` (в `.gitignore`), в репо — только `.env.example`.
- SMTP-пароль никогда не возвращается API.
- RFQ отправляет только пользовательская почта, с её адреса, с явным подтверждением.
- Внешние запросы имеют таймауты и лимиты конкурентности — сервис не «висит».

## 8. Границы прототипа (честно)

- optlist может быть пропущен (Anubis) — деградация, не блокер.
- Госплан покрывает только 44-ФЗ (осн. госсектор) — это фича для прод-обоснования цен.
- Enrich-обход ограничен N сайтами за поиск (антиспам + таймауты).
- Нет авторизации — прототип; персонификация заметок не нужна для демо.
